# On-demand functions
- `process-links`: pasted TikTok/YouTube links → posts (ScrapeCreators).
- `share`: token-checked client report data.
- `deck-view`: public side of tracked deck links (`deck.html#t=<token>`): `status`, `open` (email gate, signed 180-day viewer pass, one per link per device (Sam's rule: a viewer enters their email once per link; a different link always asks again; `localStorage` key `stellar-deck-pass:<token>`, the pass carries the link id), slide/video links signed for 2h from the private `deck-media` bucket, signed-in team not tracked), `track` (signed session id → `deck_merge`, running totals so resends never double-count). Reopening the same link with the same email within 30 minutes of the last activity continues that view (`REOPEN_MINUTES`; `open` returns the session plus `base` per-slide times the page starts from), so reloads and woken tabs make no new view and no second Slack message. Rate-limited via `deck_rate_ok` on a hashed IP; the IP is never stored. `deck.html` loads no outside fonts or scripts. `privacy.html` is the public privacy policy (Stellar Marketing ApS).
- `deck-import` (team only): builds a deck version from Figma Slides. Figma's REST API can't list what's inside a Slides file, so the slide list, links and video boxes come from the **"Send to Stellar OS" Figma button** (`figma-plugin/`, zipped as `send-to-stellar-os.zip`, rebuild the zip when its files change). Auth: the button sends a personal key (`deck_plugin_keys`, only a SHA-256 hash stored; made in Decks → Figma button); the OS sends the user's session. Slides are rendered by Figma (`/images`, `use_absolute_bounds=true`, so no white frame). TikTok videos (ID from the Snaptik layer name) are downloaded once via ScrapeCreators and reused on later versions; videos inside phone mockups keep their crop (`deck_spots.clip`). Sending the same file again makes a new version of the same deck. Needs the `FIGMA_TOKEN` secret (expires; date in `private.settings.figma_token_expires`, shown on Decks and as an OS-wide reminder in the last 14 days).
- `deck-view` email codes: a link with `verify_email` asks for a 6-digit code sent by email (Resend, secret `RESEND_API_KEY`, sender `DECK_EMAIL_FROM`, default noreply@stellarmusic.dk (live value set by the DECK_EMAIL_FROM secret); `deck_email_codes` keeps only hashes, 15 min, 5 tries). Without the secret those links fall back to a plain email gate. Sessions record `verified`. Any unused code from the last 15 minutes works (not only the newest), so a late email from spam still opens it. The code screen tells people to check spam and only offers "Send a new code" after 30 seconds. Backup when email fails: "Didn't get a code? Ask Stellar to let you in" (`help` action) → row in `deck_access_requests` + Slack message (SLACK_DECKS_WEBHOOK) → the team clicks Let in / Decline in Decks ("Waiting to be let in" panel on the list and the deck page, RPC `deck_access_decide`, team only) → the waiting page polls `help_status` and opens by itself with a verified pass (approval valid 24 h). The Resend key is send-only, so `deck-notify` `{action:"check",quiet:true}` can't list domains; DNS (one.com) has Resend DKIM (`resend._domainkey`), the `send.` subdomain and DMARC `p=none`.
- `creator-details` (public, no login): one-time payment details links, see Data model → Creator payment details.
- `vendor-form`: team actions `link` / `send` {campaign_id, email, note} (one-time link, 60 days; `send` emails it via Resend from `Stellar Invoicing <invoice@stellarmusic.dk>`, `VENDOR_EMAIL_FROM` overrides, reply-to invoice@); public `status` / `submit` (rate-limited per hashed IP) → `vendor-form.html#t=<token>`. Submit finds or makes the client (campaign's client → same company ID → unique email domain, free-mail excluded → new client, market from country), updates or adds the `client_entities` row (legal name, ID/VAT, street, zip, city, country, invoice email, `source` 'vendor form'), upserts the contact (role "Invoices"), fills the campaign (client, invoicing company, country, market, contact if empty) and posts "Vendor form" in the campaign chat. Answers + signature PNG stay on `vendor_requests` (team read-only).
- `creator-portal` (public, no login; 2026-11-25): a creator's personal page per campaign folder, `creator.html#t=<token>`. Token = link id + HMAC (`private.portal_token`, secret `private.settings.portal_secret`), checked by `creator_portal_check` (service role), so links can be copied again any time; team makes them with RPC `creator_portal_links_for(campaign, folder, creators[])`. Actions: `status`, `upload_url` (signed upload to the private `drafts` bucket, video only, ≤500 MB, max 5 waiting), `draft_done`, `withdraw`, `post_link` (only after an approved draft when drafts are on; creates a `link_jobs` row with `submitted_by` "creator @handle", so the video lands in that folder like a pasted link), `payment` (fills the roster card's PayPal details only if empty). Rate-limited per hashed IP. Tables `creator_portal_links`, `creator_drafts` (statuses submitted → changes | team_ok (waiting for the client) → approved | client_changes; withdrawn), `creator_portal_posts`. Campaign settings: `portal_drafts`, `portal_client_review`, `portal_brief`, `portal_message`. `creators.whatsapp` for pre-filled WhatsApp messages.
- `share` also serves client draft review: `{drafts:true}` (drafts of campaigns with `portal_client_review`, statuses team_ok/approved/client_changes, signed 2 h video links, hidden folders left out) and `{draft_decide, decision, note}` (team_ok → approved | client_changes; the note shows on the creator's page). The main answer has `drafts_review` so share.js adds a "Drafts" section below the report and a "N drafts to review" pill.
- `deck-notify` (pg_cron `deck-notify`, every 2 min): one Slack message per deck view, 3 minutes after the viewer leaves (who, deck, link, time, slides, top slide, links opened). Secret `SLACK_DECKS_WEBHOOK` (Slack incoming webhook); without it, it does nothing. Marks `deck_sessions.notified_at`.
- `paypal-payouts` (team session; cron via `x-deck-secret`): `check` (mode, key names, may this person pay; `verify` asks PayPal for a token, no money), `send` {campaign_id, items:[{row_id,email}]} = one PayPal batch, `sync`, `cancel` (take back an unclaimed payment). Only the campaign's runners/DRI (`team_members.name` in `campaign_runner`/`comms_owner`) or admins may pay; rows must be "Posted · to pay"; the campaign needs a PO number; creator costs must be within the creator budget. Keys: `PAYPAL_CLIENT_ID` + `PAYPAL_SECRET` (live, verified with the Payouts permission 2026-11-24), `PAYPAL_SANDBOX_CLIENT_ID` + `PAYPAL_SANDBOX_CLIENT_SECRET` (test). `private.settings.paypal_mode` = off | sandbox | live (read via `paypal_mode()`, service role only); never test with live money.
- `posts-watch` (`{campaign_id}` = check one campaign now, signed-in team; `{dry_run:true}` reads and adds nothing; cron = `x-deck-secret`): for creators on the payout sheets of active campaigns with a sound, reads their newest videos and adds the ones that use the campaign's sound to the creator's folder, the same way a pasted link is added (`link_jobs` with `submitted_by` "Stellar OS (auto)"). One fetch per creator per day (`posts_watch_checks`), even when on several campaigns. Helper `match.ts` holds the matching rules.
- `notify-email` (`{dry:true}` lists who would get what and sends nothing; cron = `x-deck-secret`): one short email per team member for the alerts they haven't read after 10 minutes, then sets `notifications.emailed_at`. Off unless `notify_email` is `'on'`.
- `artist-search`: Chartmetric (1 credit per search), falls back to Deezer.
- `creator-insights`: creator audience (Chartmetric/ScrapeCreators, cached 30 days).
- `discover`: Influencers.club. That account currently has no credits.
- `todo` (personal to-do beta): owner = email; focus areas per person in `todo_areas` (code 1–3 letters, name, `priority` 1–9; M = Meetings & calls is `builtin` for everyone; `areas_save` sets the rest + `m_priority`; Campaign Central and Sports are only offered to the emails in `private.settings.todo_area_access`, read via `todo_area_access()`, and `areas_save` refuses them for anyone else), tasks carry `area_id`, `due_kind` (eod/eow/week/day) and optional `due_time`; `snap`, `ai` and quick add read the letters (e.g. "S: call Juventus EOW"); access via OS session (email listed in `private.settings.todo_beta_users`, checked by `todo_beta_allowed()`) or a private link key (`x-todo-key`; `todo_links` keeps only its SHA-256; links made/switched off only from a signed-in session). Tables `todo_items` (status open/partial/done/dropped, `remaining`, `urgent`, `due_date`, `project`, `follows_id`, `week_start` Monday, `touched_at` = last real change), `todo_events` (history), `todo_weeks` (`recap_done_at`, `plan_done_at`). `close_week` carries open tasks to next Monday. AI (`snap` = photo of handwritten notes → tasks, photo not stored; `ai` = "1 is done but I still have to X" → proposed ops the person confirms, then `apply`) uses Claude (`ANTHROPIC_API_KEY`, model `TODO_AI_MODEL`, default claude-sonnet-5-5); without the key the rest works.
- Secret names only: PAYPAL_CLIENT_ID, PAYPAL_SECRET (PayPal payouts, live), ANTHROPIC_API_KEY (to-do AI), SCRAPECREATORS_API_KEY, YOUTUBE_API_KEY, CHARTMETRIC_REFRESH_TOKEN, INFLUENCERS_CLUB_API_KEY. The sheet web-app URL and secret are in `private.settings` (`sheet_sync_url`, `sheet_sync_secret`).
- `posts-watch` and `notify-email` are deployed but NOT scheduled. Switches: `private.settings.posts_watch` and `private.settings.notify_email` (both `'off'` until Sam says so; read by `posts_watch_mode()` and `notify_email_mode()`, service role only). The `posts-watch` cron SQL is in the comment of `20261126_posts_watch.sql` (planned `*/10` in the 01–04 UTC window). `notify-email` is planned every 5 min with `x-deck-secret`, like `deck-notify`; its cron SQL is in the comment at the end of `20261126_notify_email.sql`. posts-watch costs about 1 ScrapeCreators credit per creator per day; notify-email sends through Resend (`RESEND_API_KEY`, sender `DECK_EMAIL_FROM`).
- `fx-rates` is deployed, but its source isn't in `supabase/functions/`. Most migrations were applied through the Supabase tools, so `supabase/migrations/` is incomplete. The live database is the truth.
