# Data model essentials
- `campaigns` → `posts` → `post_daily_stats` / `post_latest_stats`; `campaign_sounds`, `campaign_markets` (16 markets), `campaign_folders`.
- `campaign_summary` view (security_invoker): spend = `creator_costs` + `payout_rows`.
- Payouts: `payout_sections` and `payout_rows`. Statuses: contacted, waiting_draft, drafted, waiting_payment (shown as "Waiting to post"), posted ("Posted · to pay", set automatically when all commissioned videos are in the tracker), paid. Rows link to creators by `creator_id` (exact handle match, or the "Same person" suggestion for near-misses). Any two of videos / price per video / total compute the third. "Sourced & paid by" only offers the campaign's runners (`campaigns.campaign_runner`, comma-separated team names) and DRI. Margin on the tab = invoiced budget − creator costs.
  - **Creator budget** = `campaigns.spend_cap_percent` (default 30) × budget, and it's a hard limit.
- Invoices: `invoice_requests`, statuses requested, returned, invoiced, paid, cancelled.
  - Exact invoicing company: `campaigns.client_entity_id` and `invoice_requests.client_entity_id` → `client_entities`. A request can be sent with "Not sure yet"; the company is picked later in the request (Invoices page) or arrives via the vendor form. Trigger `campaigns_link_entity` keeps the `invoicing_entity` text (sheet column) in step.
  - Money flags (`money.js`, `flagsFor`): no exact company; not invoiced (budget, no live request, active or a week old); request sent back; invoiced > budget (finance: credit note); budget not fully invoiced (DRI); overdue (finance). No under-spent flag (stopped campaigns = credit note). Shown under the campaign details and on Invoices → "Needs attention". They clear by themselves; no buttons to tick off.
  - Trigger `campaigns_budget_after_invoice` posts a "Stellar OS" chat message tagging finance (`@name` of role finance) when the budget changes on a campaign that already has invoiced/paid requests.
  - A trigger syncs `campaigns.invoiced`.
  - Roles live in `team_members.role` (admin/finance/member), checked with `private.is_finance()`; RPC `set_team_member` is admin only.
  - Invoice request form = Sam's finance template (`invoices.js`): responsible (DRI), client PO (`client_po`; `po_number` stays Stellar's PO), artist, song, label type (Major / Indie / Other), territory (West / Central / East), allocation by region (`allocation` jsonb), project, contact name and email, send via (UNIPORT / ARIBA / FIT / E-mail / other). Columns added by `20261126_invoice_request_template.sql`. "Request the rest" fills the amount left after earlier requests; "Copy as email" copies the request as text.
  - Invoice plan (2026-11-26, replaces the monthly retainer; Sam: "3- or 6-month retainers should all be there when we create the campaign"): `invoice_plan_parts` (label, amount, currency, `due_on` or none = when ready, `auto_request`, `request_id` → the request made for it, `reminded_at`). Guard trigger: invoiced/paid parts can't be removed or change amount; a part with a live request can't be re-linked. View `invoice_plan_part_status` (status upcoming/due/requested/returned/invoiced/paid; a cancelled request counts as not requested), view `campaign_invoice_plan_state` (per campaign: `invoice_later`, `upcoming_total`, `due_parts`), RPCs `campaign_invoice_plan(p_campaign)` and `invoice_plan_split(...)` (appends equal parts, monthly or all at once; the app removes old upcoming parts itself before a replace). Daily job: see Scheduled jobs. Money flags: no "Not invoiced yet" while the plan's parts are all in the future; "Invoice due: <label>" when a part is due. The old retainer columns (`campaigns.retainer_*`, `invoice_requests.retainer_month`) stay unused.
  - Invoices are actually sent from e-conomic. The integration isn't built yet: it's waiting on Sam's app approval (Sales role only for now).
- Alerts: table `notifications` (one row per person per alert: `kind`, campaign, title, body, in-app `link`, `read_at`, `emailed_at`, `actor`). Kinds: draft_submitted, draft_client_decision, mention, invoice_requested, invoice_status, vendor_form, deck_access, creator_post. Filled only by triggers through `private.notify(...)` (each trigger is AFTER and wrapped so an alert never blocks a write); `private.campaign_people(campaign)` = DRI + runners; `private.notify_*` triggers per kind. People read and mark read only their own rows; RPC `notifications_mark_read(ids or all)`. Realtime on inserts/updates. Alert emails are switched off (see On-demand functions → notify-email).
- Payout statuses move forward by themselves (`20261126_payout_auto_status.sql`), never backwards and never past waiting_payment: creator page first opened → at least waiting_draft; draft sent → at least drafted; draft approved → at least waiting_payment. Never sets posted or paid. Rows match by campaign + creator. Logged as automatic (actor empty).
- Sheet cost: `campaign_sheet_rows.cost` = `campaign_summary.spend` (creator costs + payout rows with an amount, in the campaign's currency, no conversion). A trigger on payout rows queues a sheet push. `private.queue_sheet_sync_campaign()` skips wrap-up-only and retainer-only edits; anyone replacing that function must keep those rules (see `20261126_sheet_sync_campaign_merge.sql`). `sync_campaign_invoiced` only writes when the value changes.
- Wrap-up checklist: `campaigns.wrapup` = manual ticks keyed by item id (who and when). RPC `campaign_wrapup(p_campaign)` = automatic checks from the data plus the ticks; `campaign_wrapup_tick(p_campaign, p_item, p_done)` sets or removes one.
- Duplicate campaign: RPC `duplicate_campaign(p_from, p_opts)` (security invoker, team only) and `duplicate_campaign_preview(p_from)` for the dialog counts. Copies only what the options ask (basics, folders, sounds, payout structure, creators, portal settings, budget). Never copies PO number, dates, notes, posts, invoice requests, payments, chat, share links, creator portal links, drafts or wrap-up ticks, so the copy can't be matched to a sheet row yet.
- Creator scorecard: view `creator_scorecard` (security invoker, team only; one row per creator): views, paid amounts in USD (latest ECB rate), cost per 1K views over paid campaigns with tracked views, drafts sent and sent back, time from first draft to post. Never exposed by `share`.
- Artist pictures: `artists` (name_key, image_url, cm_artist), filled by `artist-search` when a campaign is created or edited. The overview auto-looks-up missing ones (exact name match, max 25 per session).
- Share links: `share_links`, with settings per category; folders can be hidden.
- Folders show creators, not uploads: creators with videos in the folder plus `campaign_folder_creators` (added by profile link via the `roster` function's `lookup` action (TikTok: profile only, 1 ScrapeCreators credit; never puts them on the roster)).
- `posts.boost_code` (+ `_updated_at`, `_by`): TikTok Spark Ads code per video, team only; the `share` function selects explicit columns and never sends it.
- CSV import (`creator-import.js`, "Import CSV" on the roster): RPC `import_creators(p_rows, p_list)` (team only, max 5,000 rows) adds creators by platform + handle with no credits used; `creators.contact_email` holds the email. Imported rows have no `tiktok_user_id` until their first refresh; the AFTER INSERT trigger `creators_merge_import` folds a placeholder into the real row if `add` inserts it again (lists, folders, payouts, costs, posts move over). "Fetch their numbers now" calls `roster` `add` per new creator.
- Clients, company first (rebuilt 2026-11-25): #/clients lists every **company** (`client_entities`) grouped by label group (Independent last), with e-conomic number, client team, country, market, invoice email, campaigns and sold (USD). #/clients/co/<id> = company page (invoicing details, campaigns + revenue from the tracker and the sheet's Invoicing Entity, invoices, people, other companies of the client; Edit, Merge via RPC `merge_client_entities`, Delete only without campaigns/invoices). `client_entities` gained `economic_numbers int[]`, `phone`, `attention`, `their_ref`, `aliases` (other spellings, e.g. the sheet's old names) and `also_clients` (other teams invoicing through it). Imported from the e-conomic export: 338 customers → 329 companies (exact copies merged: same name + address), matched to the existing 31 companies by hand, 274 new clients (Sony/UMG/WMG labels put in their groups; new groups "Stellar (internal)" and "Secretly Group"). An ID-looking number in one address was dropped on import. `source` = e-conomic | vendor form | added in the OS. Older text below still describes the team (client) side:
- Clients (`clients.js`, #/clients/<client id> = team page): `client_groups` (e.g. Warner Music Group, shared `email_domains`), `clients` (one per team, e.g. Warner Brasil; `aliases` = other spellings used in the sheet, own `email_domains`, market West/Central/East, ISO country), `client_contacts`, `client_entities` (invoicing companies: legal name, VAT, address, invoice email, terms, portal). Filled from the Campaign Overview sheet on 2026-10-29. `campaigns.client_id` links a campaign; `campaigns.client` text stays for the sheet sync. Trigger `campaigns_link_client` links by name/alias when the text changes; RPCs `link_campaign_clients()` and `merge_clients(p_from, p_into)` (team only). Sheet rows are matched by client name unless their invoicing company belongs to another client. Deck viewers match by exact contact email, then a client domain, then a group domain (`loadClients().matchEmail`, also used on Decks). The campaign form's Client field picks from Clients and fills the invoicing company, location, market, type and contact; a new name can be added to Clients on save.
- Creator payment details (2026-11-24): on `creators`: `payout_method` (paypal/wise), `paypal_email`, `paypal_username`, `wise_email`, `legal_name`, `residence_country` (ISO2), `payout_note`, `payout_updated_at`/`_by` (team email, `the creator` or `form import`). Everyone on a payout sheet gets a roster card: trigger `payout_rows_roster` (BEFORE INSERT/UPDATE OF handle, creator_id, platform) links the row to the creator with that exact handle or makes a placeholder card (`roster_added_by` 'payout sheet') and sets `on_roster`. "Same person" on the Payouts tab calls RPC `merge_creators(p_from, p_into)` (team; only folds a card whose numbers were never fetched) → `private.merge_creator`, also used by `creators_merge_import`; it moves rows, costs, posts, lists, folders, PayPal payments, detail links and fills empty details. One-time links: RPC `make_creator_details_link(creator)` (team) returns a 64-hex token once, `creator_detail_links` keeps only its SHA-256, 30 days, one use, a new link voids older unused ones → `payment-details.html#t=<token>` (public, own scripts only, `countries.js`) → function `creator-details` (`status`, `submit`; rate-limited per hashed IP) writes the card. UI: roster card panel "Payment details" (autosave per field, Copy a link for them to fill in, Payments list with PO); Pay dialog prefers the card's PayPal email, shows "Prefers Wise", and offers the link when an email is missing.
- PayPal payments: `payout_batches` (one per "Pay with PayPal" click; id = PayPal `sender_batch_id` and `PayPal-Request-Id`, so retries never pay twice; `invoices` = the campaign's invoice requests at that moment) and `payout_payments` (one per creator; id = `sender_item_id`; `po_number` and `note` "Stellar · PO <po> · Artist – Song", which PayPal shows the creator; statuses queued/pending/success/unclaimed/onhold/failed/returned/blocked/refunded/reversed/denied/canceled; `env` live/sandbox). Team can read both, nobody but the function can write. Unique index: one queued/pending/success/unclaimed/onhold payment per payout row. `payout_rows.paypal_email` (also saved to `creators.paypal_email`). On success the row becomes Paid (`paid_via` paypal); a refund/reversal after success puts it back to "Posted · to pay". UI: Payouts tab (tick "Pay" in the Paid column → "Pay with PayPal" review dialog: emails, total, PO note, invoice(s), creator budget left; status pills; "PayPal payments" history; polls every 20 s while sending), Payouts page "Sent with PayPal" (search by PO, invoice, creator, campaign; region). Campaigns with payments can't be deleted (FK restrict).
- Creator avatars are copied to the `avatars` bucket by both `roster` and `process-links` (TikTok's own links expire).
